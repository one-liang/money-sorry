## Context

專案目前有兩頁，各自完整、刻意不共用程式碼：

| | 開啟方式 | 預覽實作 | 狀態 | 輸出 |
|---|---|---|---|---|
| `index.html` 套框 | 雙擊 `file://` | `img` + `img` 兩層 DOM，拖曳只改 CSS 幾何 | `item.adjust {z,dx,dy}`、`item.measure.content` | 1000×1000 JPEG 0.92 |
| `censor.html` 遮罩 | 必須 `http://`（22MB 模型） | 單一 canvas，每格 repaint（`curBmp` 常駐） | `item.boxes[]`（原圖座標）、`item.areaPct` | 原尺寸 JPEG 0.92 |

兩者的耦合點只有一條：**遮罩座標在原圖空間，套框把圖裁縮成 1000×1000**，所以順序必須是先遮後套。這條規則目前寫在 README 裡靠人腦執行。

`index.html` 的外框以 base64 內嵌，是為了規避 `file://` 下的 canvas taint；它的「單一檔案、雙擊即用」是專案賣點，`censor.html` 原始碼裡明確記載了「不抽共用檔就是為了保住這個性質」。

已有的驗證資產：`tools/verify/censor.mjs`、`tools/verify/preview-adjust.mjs`。後者示範了一個關鍵手法——`git show v1.2.0:index.html` 起一份基準頁面、實跑一次比 SHA-256，用來證明「沒動過的照片輸出逐位元相同」。

## Goals / Non-Goals

**Goals:**

- 一次上傳完成遮罩與套框，順序由程式保證而非文件提醒
- 全程只做一次 JPEG 編碼（現行雙頁流程會編兩次）
- 每張照片可各自決定要不要套框、要不要遮罩
- 批次輸出可統一命名、可排序、可追加
- `index.html` 零修改；`censor.html` 可觀察行為零變化
- 四格輸出中三格能自動驗到逐位元

**Non-Goals:**

- 不改 `index.html` 的任何一行
- 不改變 `censor.html` 的輸出、UI 或互動
- 不引入 build 步驟、不引入外部套件、不使用 ES module
- 不做多張拼貼版型、不做馬賽克／模糊／非矩形遮罩
- 不提供「一鍵關閉全部遮罩」

## Decisions

### D1：新增第三頁，而不是併進既有任一頁

考慮過三條路：

| | 保住 `index.html` 雙擊即用 | 要重寫的部分 |
|---|---|---|
| 併進 `index.html` | 可（模型延遲載入） | 預覽多疊一層 canvas；但 `index.html` 從此不再是可單獨寄出的一個檔案 |
| 併進 `censor.html` | — | **構圖調整整套重寫** |
| **新增 `studio.html`** | 完全不受影響 | 無 |

排除「併進 `censor.html`」的理由最硬：構圖調整是全專案投資最深、驗證最嚴的部分（`preview-adjust.mjs` 釘了三個不變量，其中一個是與 `v1.2.0` 逐位元相同），搬家等於把最脆弱的東西重做。反方向（遮罩往外搬）只是「畫矩形 + hit test」，沒有與輸出對齊的隱性契約。

最終選新頁：兩個既有入口都零風險，代價是重複程式碼——由 D9 處理。

### D2：單次合成管線，遮罩框走同一組仿射參數

`srcRect()` 已經把「去白邊 + cover + 手動調整」壓成單一來源矩形 `{sx, sy, sw, sh, f}`，且 `sw === sh`，所以只有一個等向倍率。遮罩框從原圖座標換到輸出座標只需要：

```js
outX = (box.x - r.sx) * r.f
outY = (box.y - r.sy) * r.f
outW = box.w * r.f          // outH 同理
```

合成順序：

```
canvas 1000×1000
  ① 白底（去背 PNG 轉 JPEG 才不會變黑）
  ② drawImage(bmp, r.sx, r.sy, r.sw, r.sh, 0, 0, 1000, 1000)
  ③ 遮罩開 → fillRect(換算後的框)     ← 邏輯上「在套框之前」
  ④ 套框開 → drawImage(frame, 0, 0, 1000, 1000)
```

**沒有中間畫布，沒有二次編碼。** 現行雙頁流程是「遮罩 → JPEG 0.92 → 重新解碼 → 套框 → JPEG 0.92」，合併後只在 ④ 之後編一次。

框被裁到畫面外是安全的：裁切只會切掉黑色矩形的一部分，露出來的區域本來就不在輸出裡。反方向不安全，見 D4。

替代方案：先在原尺寸畫布畫遮罩、再把該畫布當來源做裁切。多一個全尺寸畫布（4000×3000 RGBA 約 48MB）且多一次重取樣，沒有任何好處。

### D3：四格輸出矩陣，三格可逐位元釘死

| 套框 | 遮罩 | 輸出 | 重編碼 | 驗證基準 |
|---|---|---|---|---|
| ✗ | ✗ | 原始位元組直接進 ZIP，副檔名跟隨原圖 | 否 | 輸出位元組 === 輸入位元組 |
| ✗ | ✓ | 原尺寸 JPEG 0.92 ＋黑框 | 是 | 與 `censor.html` 逐位元相同 |
| ✓ | ✗ | 1000×1000 JPEG 0.92 ＋外框 | 是 | 與 `index.html` 逐位元相同 |
| ✓ | ✓ | 1000×1000 JPEG 0.92 ＋黑框＋外框 | 是 | 無基準：預覽↔輸出像素比對 ＋ 人眼 |

三格自動釘死等於證明「新頁沒有動到任何一條既有路徑」。而且因為 `index.html` 與 `censor.html` 都保留在現役，基準頁不必從 git tag 撈——直接跑那兩頁就是基準，比 `preview-adjust.mjs` 現行做法更簡單。

「兩個都關」選擇**真的原樣**（原始 `File` 的位元組），而不是重編成 JPEG 求副檔名一致。理由：那是唯一無損的一格，重編是無謂的畫質損失，而且「原樣」這個承諾一旦打折就沒有意義。代價是 ZIP 內可能混雜 `.jpg` / `.png` / `.webp`，由清單上的「原圖原樣」標示說明。

### D4：雙模式預覽——兩個模式看到的東西不同

這不只是手勢分配問題。**兩個編輯動作需要的視野本質上不同：**

```
編輯遮罩模式                          調整構圖模式
┌───────────────────────┐            ┌──────────────────┐
│  完整原圖 2000×3000    │            │▛▀▀▀▀▀▀▀▀▀▀▀▀▀▀▜│
│ ┌┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┐   │            │▌ [橫幅]        ▐│
│ ┊  ┌──┐          ┊   │            │▌  ┌──┐         ▐│
│ ┊  │██│ 可拖可改  ┊   │    ←→      │▌  │██│ 唯讀    ▐│
│ ┊  └──┘          ┊   │            │▌  └──┘         ▐│
│ └┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┘   │            │▙▄▄▄▄▄▄▄[橫幅]▟│
│  ┌──┐  ↑虛線＝裁切範圍 │            └──────────────────┘
│  │██│ ← 這個會被切掉   │             所見即輸出
│  └──┘                  │
└───────────────────────┘
```

驅動這個設計的是一個**單向漏遮風險**：

> 只在裁切後的視野裡確認「都遮好了」，之後把構圖拉遠一點，原本在視野外、未被遮的部位就會進入輸出。

反過來（拉近讓遮罩被切掉一部分）安全。因此遮罩編輯必須在完整原圖視野下進行，並以虛線標示哪些區域會被裁掉。

| | 編輯遮罩 | 調整構圖 |
|---|---|---|
| 視野 | 完整原圖 ＋ 虛線裁切範圍 | 1000×1000 裁切結果 |
| 外框 | 淡出 | 固定疊上 |
| 單指拖曳 | 畫新框 | 平移照片 |
| 遮罩框 | 可拖、可改、可刪 | 唯讀，跟著照片動 |

**預設模式跟著遮罩開關走**：遮罩關 → 模式切換整個不出現，行為 100% 等同今天的 `index.html`；遮罩開 → 預設進「編輯遮罩」。預設進編輯遮罩是因為兩件事頻率差很多——構圖是「切壞時才喬」（少數張），遮罩是「私處召回只有一半，務必逐張確認」（幾乎每張）。

預覽 DOM 疊三層，`layout()` 把同一組幾何寫進照片與遮罩層：

```
#pview（視窗，overflow hidden）
  ├─ <img id=pphoto>       left/top/width/height 以 % 寫入
  ├─ <canvas id=pboxes>    同一組幾何，跟著照片動
  └─ <img id=pframe>       inset:0，固定不動
```

替代方案：整個預覽改用單一 canvas 每格重畫。`index.html` 當初否決過（大圖合成 100~500ms），不過那個成本主要來自 `createImageBitmap`；只要 bitmap 常駐（`censor.html` 已經這樣做），重畫其實夠快。仍選三層方案，因為它讓「遮罩關」的路徑與 `index.html` 完全同構，D3 的逐位元不變量比較容易維持。

### D5：開關用晶片，一鍵兩個方向都給

清單列已經有縮圖、檔名、尺寸、輸出名與 badge，再塞兩個標準 switch 會把列撐高，掃 30 張很累。改用兩個可點擊的晶片（亮＝開、暗＝關），壓在同一排。

```
┌────────────────────────────────────────────┐
│ ┌──┐                                       │
│ │01│ [img] figure-01.jpg      ⬚套框 👁遮罩 │
│ │⣿ │       820 KB · 2000×3000        ↑     │
│ └──┘       商品-01.jpg · 3 個遮罩    │     │
│   ↑                                  └ 點晶片＝切開關
│   └ 序號＋把手合成一欄：只有這裡可拖＝排序
└────────────────────────────────────────────┘
```

序號放在最左邊、字級比檔名大、用等寬數字，是因為它決定 ZIP 裡的排序，卻很容易被淹沒在一排標籤裡。把它跟拖曳把手合成同一欄還有兩個附帶好處：觸控目標一次做到 46px（超過 44×44 的下限），而且「要改順序就抓這個數字」的因果關係是自明的。

一鍵為套框與遮罩**各給一組「全開／全關」**。曾經考慮過只給全開——依據 `nudity-censoring` 的取捨原則，漏遮會導致商品下架、多遮只是醜，而批次關閉不會在畫面上留下痕跡。實際使用推翻了這個顧慮：整批只想套框時，逐張關 30 個遮罩開關的成本太高。

但兩個方向都給之後，原本的形狀就開始說謊：兩顆按鈕擠在同一個 pill 裡，那是分段控制器的形狀，**暗示「其中一個是目前狀態」，實際上卻永遠沒有任何一段被點亮**。這違反 `ui-ux-pro-max` 的 Active State 規則。所以一鍵區改成真的有狀態：

```
整批套用
  套框      30 / 30 張        [ 全開 ][ 全關 ]     ← 全開那段點亮
  遮罩      12 / 28 張        [ 全開 ][ 全關 ]     ← 混合，兩段都不亮
            ⚠ 其中 2 張沒偵測到任何部位，輸出時不會有遮罩
```

- **計數是權威來源，點亮只是視覺冗餘。** 因此刻意**不用 `aria-pressed`**：那會宣告「這是可取消的切換鈕」，但按第二次是無操作，等於承諾做不到的事。改用 `data-state="lit"` 驅動 CSS，狀態以文字形式提供給輔助技術。
- **已在目標狀態時不設 `disabled`。** 焦點停在被 disable 的按鈕上會掉回 `<body>`，下一次 Tab 得從文件最上方重來（WCAG 2.4.3）。改為無操作 ＋ 一次 350ms 的回彈，表示「有收到，只是沒事可做」。
- **只動真的需要改變的項目。** 原本無條件 `it.cache = null` 會把 30 張已編好的 JPEG blob 全丟掉，即使那張根本沒變。
- **作用域對齊到 `outputtable`**：計數的分母、輸出按鈕的張數、實際被改到的項目必須是同一個集合，否則畫面上的數字會互相矛盾。
- 拿掉標籤旁的 icon——每一列的晶片已經有同一組 icon，重複了。

考慮過但未採用的比例填充條（在計數旁加一條 40% 填滿的橫條）。它的好處是混合態**有形狀**，而目前混合態是用「沒有任何一段亮」表達，與「元件沒生效」在視覺上不易分辨。計數文字是目前唯一的區分依據。

### D5-b：不對稱的風險，就用不對稱的守護

四顆一鍵按鈕裡只有一顆是危險的：

| | 全開 | 全關 |
|---|---|---|
| 套框 | 無害 | 無害（圖不好看） |
| 遮罩 | 無害（只是慢） | **可能漏遮下架** |

所以只有「遮罩‧全關」掛復原，其餘三顆維持一觸即發，不對無害的操作收確認稅：

```
狀態列 ▸ 已關閉 28 張的遮罩　[ 復原 ]
```

復原**幾乎是免費的**：`bulkSet` 只動 `censorOn` 與 `cache`，`boxes` 與 `detect` 原封不動；而 `runDetections()` 的待辦清單只挑 `detect === 'idle'`，所以復原是 O(1) 的旗標寫回，**不會觸發第二輪偵測**。

為什麼不用兩段式確認（像「清空」那樣）：armed 狀態（紅色、寫著「確定？」）與「點亮＝目前狀態」是互斥的語意，同一顆按鈕擔不了兩個角色。

### D5-c：計數必須數效果，不是意圖

原本 `withCensor` 數的是 `censorOn`，沒管 `boxes.length`。**偵測完成但一個部位都沒抓到的那張，輸出時完全沒有遮罩**，卻被算進「12 張含遮罩」——那是一個灌水的保證。把它做成常駐 HUD 只會把錯誤放大。

改成 `censorOn && boxes.length > 0`，並把「N 張沒偵測到任何部位」從 `#status` 移到一鍵區常駐。原本那句話寫在 `#status`，會被後續的「輸出中 N / M…」整個蓋掉——**下載前最後一眼永遠看不到它**，而那正是它唯一該出現的時機。

### D6：輸出命名的四個變數

一個輸入同時決定四件事，所以必須看得到結果——用文字解釋一定講不清楚。原本做了一塊集中的預覽區（`ZIP 檔名 › 資料夾 › 首末檔名`），後來拿掉了：那是把資訊搬離它所描述的對象。改成**每一列直接標出自己的輸出檔名**，配合最左邊的序號，因果關係當場成立，也不必再維護一個會與清單失準的第二事實來源。

```
輸出命名 = 「錢錢抱歉」，共 30 張

  錢錢抱歉.zip          ① ZIP 檔名
  └── 錢錢抱歉/         ② 資料夾名
        錢錢抱歉-01.jpg ③ 檔名前綴 ＋ ④ 序號
```

檔名帶前綴（而非只有 `01.jpg`），因為賣場上傳通常是把檔案拖出資料夾，資料夾名當下就消失了。

- **未命名**：ZIP 沿用 `money-sorry-<YYYYMMDD>-<HHMM>.zip`，內層資料夾同名，檔案沿用原檔名加後綴
- **一律開一層資料夾**：解壓到桌面不會噴 30 個檔案出來
- **序號補零依總數**：9 張以下 `1..9`，10~99 張 `01..30`。不補零時多數工具會把 `10` 排在 `2` 前面
- **跳號連號重排**：30 張裡 3 張失敗 → 輸出 `01..27`，不留洞。留洞會讓人以為漏抓了檔案
- **檔名消毒**：`/ \ : * ? " < > |` 與前後空白、句點一律清掉，避免在 ZIP 內造出詭異路徑。中文安全，flag bit 11 已設 UTF-8
- **單張仍不打包**，直接給檔案，因此沒有資料夾

### D7：拖曳排序用 pointer events，而且不用 pointer capture

`#drop` 已在監聽 `dragenter/dragover/drop` 收外部檔案。內部排序若也走 HTML5 DnD，得靠 `dataTransfer.files` 是否為空去分辨兩者，很脆。pointer events 完全繞開，觸控行為也一致。

**但不能用 `setPointerCapture`。** 排序過程要把被拖的 `<li>` 搬到別的位置，而 Chrome 在元素被重新插入 DOM 時會釋放它的 pointer capture——之後的 `pointermove` / `pointerup` 就再也送不到它身上，收尾函式不會執行，`.dragging` 與選取狀態就卡在畫面上。改成把 move/up 掛在 `window` 上完全避開。

動畫用 **FLIP**：搬動前記下各列的 `offsetTop`，搬完再量一次，把差值當成起點反推回去讓瀏覽器補這段位移。只動 `transform`，不動 `width/height`，時長 180ms（落在 UX 準則的 150–300ms 內），並在 `prefers-reduced-motion: reduce` 時整個略過。刻意用 `offsetTop` 而非 `getBoundingClientRect()`——後者會量到其他列動畫進行中的中間值，落點判斷會抖。

被拖的那一列自己不吃 FLIP，而是跟著指標 `translateY`。每次搬動都會改變它自己的版面位置，所以要把差值累加進一個 `shift` 補償，手指底下的那一列才不會跳掉。

排序後必須連動三件事：序號即時重編（這是最直接的落點回饋）、`selected` 跟著原本那張照片走、以及**選取狀態一律由 `selected` 重新推導**而非增量維護——增量維護正是選取殘留的來源。

只有把手可拖，不是整列可拖，否則「點一列切換預覽」會在手指稍微移動時被判成排序。並提供鍵盤替代（把手聚焦時 `↑/↓` 移動，同樣走 FLIP），因為純拖曳沒有鍵盤路徑。

**為什麼不引 SortableJS 之類的套件**：這個專案刻意零依賴、零 build，連 ZIP 都是手寫的。這裡真正的問題只有「capture 掉了」一個，修掉就好，不值得為它多背一個 45KB 的 vendor 檔與一套自己的事件模型。

### D7-b：序號與把手要分開

序號與把手一度合成同一個 `<button class="rail">`（40×52，有底色與邊框），理由是湊出夠大的觸控目標。但那讓**唯讀資訊被包進了控制項**：序號是輸出順序的讀數，卻長得可以按；螢幕閱讀器也只念得到「拖曳排序」，數字被整個吃掉。

拆成兩件：

```
 01   ⣿   [縮圖] 檔名.jpg              [套框][遮罩]
 ↑    ↑
 │    └ <button class="grip">：唯一的拖曳表面
 └ <span class="ord" aria-hidden="true">：純文字讀數
```

- `.ord` 設 `aria-hidden`，因為 li 的 `aria-label` 已經念過「第 N 張」。但這也代表**視覺上那個「–」（不會輸出）在聽覺上會消失**，所以 aria-label 要補成 `不會輸出，檔名.jpg`。
- 容器 `<ul>` 補上 `role="listbox"`。每個 `li` 早就有 `role="option"`，沒有 listbox 的話那是孤兒角色，各家輔助技術行為不一致——而上面整套 `aria-hidden` 策略正是押注在「li 的 aria-label 會被念出來」。
- **視覺窄、命中區大**：`.grip` 視覺 24px，用 `::before { inset: -6px -8px -6px -2px }` 把實際命中區擴到約 34×64，面積超過 44×44 的下限。
- `touch-action: none` **只留在 `.grip`**。若整條前導欄都設，手機從清單左緣往上滑會完全捲不動——那是一條貫穿 30 列的死帶。
- 拆開後失去了底色塊那個 affordance，改由 `li:hover` 時整條前導欄一起變色承接。grip 的六點**恆常可見**而非 hover 才顯色——觸控裝置沒有 hover，任何 hover-only 的提示在手機上等於不存在。

**已知代價**：那個最顯眼的數字現在是死區，使用者可能會去壓它拖曳而沒反應。這是「乾淨分離」的必然結果。若實際用起來覺得難抓，回頭可以讓 `.ord` 在 `pointerType === 'mouse'` 時也當拖曳表面，觸控維持不吃，這樣不會犧牲捲動。

### D12：圖示一律用 Lucide，不用文字符號

原本用 `⠿`／`◱`／`●`／`−`／`+`／`▸` 這類 Unicode 字元當圖示。它們在不同平台的字重與基線差很多，而且 UX 準則把「用 emoji／文字符號當圖示」列為明確的反模式。

改用 [Lucide](https://lucide.dev/icons)（MIT），兩種內嵌方式：

- **inline SVG**（`.ic`）：一般情況。只存 path 資料，外框屬性由 `svgIcon()` 統一補，顏色與線寬跟著 CSS 的 `currentColor` 走
- **CSS mask + data URI**（`--ic-chevron`）：需要跟著 `:hover` 變色又不方便加節點的地方，例如 `<summary>` 的 `::before`

一律內嵌，不打 CDN——三頁都要能離線運作，`index.html` 更是必須維持單一檔案。

### D8：選檔改為追加，另設清空

追加時**既有 items 的 `boxes` / `adjust` / `measure` 一律不碰**，只 append，且不得搶走目前選取——正在逐張確認遮罩時被拉回第一張很煩。連帶：`revokeObjectURL` 只能在真正清空時執行。

同一個檔案被選兩次會靜默產出兩張一模一樣的成品（統一命名後序號天生不撞，`dedupe()` 不再留下痕跡）。以 `name + size + lastModified` 判定並在該列標「重複」——不擋，但看得見。

「清空」丟掉的是全部遮罩編輯與構圖調整，可能是半小時的工作，比一鍵全關遮罩嚴重得多。因此：放在清單標頭右側的次要位置（不與一鍵按鈕並排成同等權重）、按鈕上寫出數量 `清空 (30)`、按下需確認。

### D9：`lib/` 的界線

`studio.html` 本來就需要 server（模型），所以它**沒有單一檔案的包袱**，可以自由 `<script src="./lib/zip.js">`（classic script，不是 ES module，不需要打包）。`censor.html` 早就在 `<script src="./vendor/ort.wasm.min.js">`，同樣沒有包袱。

```
index.html    內嵌一份            ← 保住「單一檔案、雙擊即用、可寄給別人」
censor.html   <script src="./lib/zip.js">
studio.html   <script src="./lib/zip.js">
```

重複度 2 份而非 3 份。`nudity-censoring` 現行要求「兩頁 MUST NOT 共用程式碼」，該條款的真正目的是保護 `index.html`，需重新界定為「MUST NOT 與 `index.html` 共用」。

`censor.html` 的抽換以 `tools/verify/censor.mjs` 加上「輸出與抽換前逐位元相同」驗收。若驗證未過就退回讓 `censor.html` 保留自己那份（3 份），不阻擋本變更其餘部分——這組任務刻意可分離。

### D10：模型延遲載入

`studio.html` 雖然本來就要 server，但「整批只套框」是常見情境，沒必要每次都先吃 22MB。因此遮罩開關**預設關閉**，首次有任一張啟用遮罩時才開始下載模型，並沿用 `censor.html` 的進度條與失敗訊息。

模型載入失敗時，遮罩開關 MUST 全部退回關閉並顯示錯誤——絕不能表現成「偵測到 0 個部位」，那會讓人以為圖片是安全的。

### D11：遮罩面積警示改用裁切後的分母

`censor.html` 的 `maskedRatio()` 以原圖面積為分母，超過 `AREA_WARN = 0.35` 就警告「遮完可能不能用」。套框啟用後畫面被裁掉一塊，同一組遮罩的實際佔比更高——沿用原分母會往「太寬鬆」的方向失準。套框開啟時，分母 MUST 改為裁切後的可見區域，且只計入落在該區域內的遮罩面積。

## Risks / Trade-offs

**[單向漏遮：在裁切視野確認完成後拉遠構圖]** → D4 的雙模式視野切換；編輯遮罩時強制顯示完整原圖與虛線裁切範圍。

**[沒有「一鍵全關遮罩」會被嫌麻煩]** → 刻意的不對稱（D5）。真的需要整批不遮，等於不該用遮罩開關，直接一張都不開即可。

**[抽 `lib/` 動到現役的 `censor.html`]** → 以 `censor.mjs` ＋輸出逐位元比對驗收；該組任務可分離，驗不過就退回 3 份複製，不影響 `studio.html` 上線。

**[三頁並存，使用者不知道該點哪個]** → 導覽列把 `studio.html` 排第一並標示為建議入口；另外兩頁的說明列各加一句指向新頁。

**[追加沒有上限，30 張變 300 張時記憶體吃緊]** → 沿用既有的逐張序列處理與即時釋放策略；`items` 只存 `File` 參考與框座標，不存解碼結果，僅目前預覽那張的 bitmap 常駐。

**[混雜副檔名（`01.jpg` 旁邊出現 `03.webp`）造成困惑]** → 清單該列標「原圖原樣」，並在使用說明中寫明兩個開關都關即為原檔轉存。

**[「兩個都開」那一格沒有逐位元基準]** → 以預覽↔輸出的像素比對涵蓋構圖正確性；遮罩位置正確與否本來就只能人眼判斷（`censor.mjs` 已有同樣的收尾提醒）。

## Migration Plan

新增為主、修改為輔，沒有資料遷移：

1. 抽 `lib/zip.js`，`censor.html` 改為引用，跑 `censor.mjs` 並比對輸出逐位元相同（此步驟可獨立回退）
2. 新增 `studio.html`，三頁導覽列同步更新
3. 新增 `tools/verify/studio.mjs`，釘住 D3 的三格不變量
4. 更新 `README.md`：三個工具的對照表、新頁的使用方式、「先遮後套」那條規則改註明僅適用於分頁流程

回退：刪除 `studio.html` 與導覽列第三個 tab 即可，另外兩頁不依賴它。若步驟 1 出問題，還原 `censor.html` 並讓 `studio.html` 自帶一份 ZIP 實作。
