## Context

`studio.html` 目前只有一個素材入口：`<input type="file">` 與拖放。使用者的實際流程在這之前還有一段完全人工的前置——開 amiami 商品頁、右鍵另存 11 張圖、複製兩段說明文字。本設計把這段接進來。

三道牆的實測結論（詳見 proposal）決定了整個架構：**網頁拿得到 amiami 的圖片網址，拿不到圖片位元組**。而 `studio.html` 的合成管線 `File → createImageBitmap → canvas → toBlob` 要的正是位元組。所有設計選擇都圍繞這一句話。

既有的約束不變：零 build、零後端、classic script、`index.html` 維持單一檔案可攜、照片不離開瀏覽器。

## Goals / Non-Goals

**Goals**
- 貼一個 JAN，圖片進清單、內文備好，銜接既有的一鍵套框與一鍵遮罩
- 匯入項目與選檔項目**在資料結構上完全同構**，既有能力零成本繼承
- 外部相依的失敗是明確可見的，且不波及任何本機功能

**Non-Goals**
- 不做翻譯（內文原樣日文）
- 不支援 amiami 以外的來源
- 不做離線備援（「拖入已存網頁資料夾」）——留待相依真的出問題再議
- 不新增後端、擴充、build 步驟

## Decisions

### D1：以兩個公用代理取得資料，而非後端／擴充／剪貼簿

| 方案 | 過 CORS | 過 Cloudflare | 取得位元組 | 代價 |
|---|:---:|:---:|:---:|---|
| 純前端直接 fetch | ✗ | — | ✗ | — |
| 本機或雲端 proxy | ✓ | **✗ 實測 403/429** | ✗ | 要主機 |
| headless browser（Playwright） | ✓ | ✓ | ✓ | +300MB、軍備競賽 |
| Chrome 擴充 | ✓ | ✓ | ✓ | 多一個要維護與安裝的產物 |
| 剪貼簿逐張貼上 | ✓ | ✓ | ✓ | 11 次手動操作 |
| **r.jina.ai ＋ images.weserv.nl** | **✓** | **✓** | **✓** | **外部相依** |

選最後一列，因為它是唯一同時滿足「保住貼 JAN 的體感」與「不新增任何安裝或後端」的組合。`r.jina.ai` 內部跑 headless browser，等於把「必須有人扮演瀏覽器」這件事外包；`images.weserv.nl` 以 `access-control-allow-origin: *` 重新提供位元組，順帶解掉 canvas 汙染。

放棄擴充方案的理由不是它做不到（它做得到，而且更穩），而是它把一個純靜態專案變成「靜態頁 ＋ 需安裝的伴生產物」。若日後代理不可用，擴充仍是備案。

### D2：匯入的圖片走既有的 `accept()`，不另闢路徑

`accept(fileList)` 內部是 `[...fileList]`，接受任何可疊代的 `File` 集合。因此：

```
weserv Blob → new File([blob], name, {type, lastModified:0}) → accept([...files])
```

之後的雙開關、一鍵區、拖曳排序、輸出命名、序號、量測、遮罩偵測、ZIP 打包**全部原樣適用**，不需要任何分支。「匯入的圖片可以一鍵套框與一鍵遮罩」這個需求因此不是新功能，而是同構帶來的結果。

替代方案（為網路來源另設一種 item 型別）被否決：它會讓四格輸出矩陣、序號規則、面積警示等既有不變量各自多一條例外，是純粹的複雜度成本。

**`lastModified` 固定為 `0`**。`accept()` 的重複判定鍵是 `name|size|lastModified`，若用 `Date.now()`，同一個 JAN 匯入兩次不會被標示為「重複」。固定值讓重複偵測對匯入項目正常運作。

### D3：解析邏輯抽到 `lib/amiami.js`，與 UI 分離

抽出的理由是**可驗證性**：搜尋結果擷取、圖片清單組成、`#explain` 擷取這三件事都是純函式（`Document → 資料`），可以對固定的 HTML 樣本離線驗證，不必每次跑真實網路請求。網路請求本身留在薄薄一層 fetch 包裝裡。

依既有規格，`lib/` 為 classic script，且 `index.html` MUST NOT 引用。

### D4：擷取規則錨定在 amiami 的實際 DOM

實測確認（`FIGURE-206235`）：

```
搜尋頁   #search_table .product_box a[href*="gcode="]      ← 只含搜尋結果，不含推薦商品
商品頁   [data-main-image]      → 主圖 600×600
         [data-item-image] × N  → 圖庫 800×~750（非正方形）
         #explain > *           → 規格與解說，排除 .hashtag-container
```

`<br>` **MUST 還原為換行**。`textContent` 會把規格黏成 `【サイズ】全高：約140mm【素材】プラスチック` 一長串；正確結果應為逐行。

`.hashtag-container` 在 `r.jina.ai` 的 HTML 快照中不一定出現（它是 JS 後渲染的）。排除規則仍 MUST 保留——它在使用者直接檢視的頁面上確實存在，且成本為零。

商品名取自 `<title>`，MUST 清除 `-amiami.jp-…` 站名後綴。

### D5：JAN 歧義由使用者裁決

同一個 JAN 在 amiami 可能對應多筆（予約／再販／中古）。

| 結果 | 行為 |
|---|---|
| 0 筆 | 明確錯誤，清單不變 |
| 1 筆 | 直接匯入 |
| N 筆 | 列出候選（縮圖＋名稱），由使用者選 |

自動取第一筆被否決：使用者無從發現拿錯了商品，而錯誤要到上架後才會顯現。

### D6：內文的兩個落點

- **落點 A** — 頁面面板，規格與解說各自可複製，另有「全部複製」
- **落點 B** — ZIP 內的 `.txt`，檔名跟隨輸出命名（`錢錢抱歉/錢錢抱歉.txt`；留白時沿用既有的 `money-sorry-<YYYYMMDD>-<HHMM>` 規則）

**既有規則「輸出單張時直接下載、不打包」在存在內文時 MUST 讓步為打包。** 否則文字無處可去。這是刻意的例外，理由是「不打包」的目的是替使用者省一次解壓，而當有第二個檔案要交付時這個理由就不成立了。

多次匯入時，`.txt` 內以商品名分段累積，而非只保留最後一次——清單本來就可以混合多個商品。

### D7：並發上限 4，部分失敗不中止

demo 以 11 張全並發成功，但公共服務的限流沒有保證。取 4 為上限，代價是數秒鐘，換到的是不會整批因突發限流而失敗。

部分失敗時，成功的圖片照常入列，失敗數量明確回報。這與既有規格「無法解碼的檔案…MUST 繼續處理其餘檔案，MUST NOT 中止整批作業」同一個立場。

內文擷取失敗與圖片失敗互相獨立——只拿到圖也是有用的結果。

### D8：隱私界線必須明說

README 的核心承諾是「照片全程留在這台電腦」。匯入功能會向第三方發出請求，若不說明，等於默默地讓這句話變得可疑。

實際界線是：**送出的只有 JAN 代碼與 amiami 的公開網址；使用者自己的照片完全不參與，一個位元組都不會離開瀏覽器。** 這句話 MUST 出現在 UI 的匯入區塊與 README。

## Risks / Trade-offs

- **外部服務是單點故障**（限流、改政策、停止服務）→ 失敗時明確報錯並保留既有清單；不自動重試以免把限流變成雪崩；擴充方案作為日後備案
- **jina 的 HTML 快照可能與實際頁面有落差**（如 `.hashtag-container` 缺席）→ 擷取規則以「存在就處理，不存在也不算失敗」的方式書寫，不對可選區塊做硬性斷言
- **amiami 改版會打斷擷取**（class 或 attribute 更名）→ 解析為純函式且有固定樣本驗證，改版時修一個地方即可；擷取不到時報明確錯誤，MUST NOT 悄悄產生空結果
- **weserv 的輸出不保證與 amiami 原始位元組相同** → 既有的「兩者皆關＝原始位元組原樣」對匯入項目仍然自洽（輸出的就是收到的位元組），但它比對的對象是 weserv 的輸出而非 amiami 的原檔，規格需點明
- **上架素材的著作權** → 工具不做判斷，此為使用者上架時的既有責任，與本變更無關

## Migration Plan

單向新增，無資料遷移。匯入區塊在未使用時對既有流程零影響；rollback 即為移除該區塊與 `lib/amiami.js`。
