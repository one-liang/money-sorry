## Context

`index.html` 是零相依、可離線（`file://`）開啟的單檔工具。合成管線目前是：

```
file → createImageBitmap(imageOrientation:'from-image')
     → coverRect(bmp.width, bmp.height)      // 以原始尺寸算縮放
     → drawImage(bmp, 裁切矩形 → 0,0,1000,1000)
     → drawImage(frame, 0,0,1000,1000)
     → toBlob('image/jpeg', 0.92)
```

實測資產：

| 物件 | 事實 |
|---|---|
| `assets/frame.png` | 1000×1000 RGBA，中央透明；左右邊條約 20px 不透明；左上／右下兩條不透明斜幅 |
| 範例來源圖 | 1000×1000，四角皆 (255,255,255)；內容 x∈[114,884] → **771×1000**；上下無留白（內容貼齊 y=0/999） |

範例圖走現行管線：`max(1000/1000, 1000/1000) = 1` → 不裁不縮，白邊原樣進成品。

## Goals / Non-Goals

**Goals:**

- 預覽可切換到清單中任一張，且在非同步合成下不會顯示錯張。
- 自動移除單軸的純色淺色留白邊，讓實際內容等比放大填滿 1000×1000。
- 誤判可被使用者一眼發現（清單顯示去邊量）。

**Non-Goals:**

- 不做去背、不輸出含 alpha 的 PNG。「把白邊變透明」在本設計中等價於「把白邊排除在來源裁切矩形之外」，中間不產生透明點陣資料。
- 不處理漸層留白邊、不處理帶陰影／浮水印的邊。
- 不做智慧主體偵測（saliency）決定裁切錨點；固定置中。
- 不加去邊開關；行為固定，改以顯示去邊量取代開關。

## Decisions

### D1. 留白邊偵測：四角取樣 + 淺色閘門 + 逐邊整列掃描

判定順序：

```
1. 掃描畫布：把 bitmap 繪到最長邊 ≤ 512 的離屏 canvas，getImageData 一次
2. 四角各取 5×5 中位數 → c0..c3
3. 淺色閘門：四角亮度（0.299R+0.587G+0.114B）皆 ≥ 215      → 否則不裁
4. 一致性閘門：四角之間任一通道最大差 ≤ 12                  → 否則不裁
5. bg = c0..c3 平均；isBg(p) ⟺ 每通道 |p-bg| ≤ 12 或 alpha < 8
6. 逐邊由外往內掃：整列（或整行）全為 isBg 才算留白，遇到第一列非全 bg 即停
7. 軸向規則（見 D2）
8. 把掃描座標換算回原始像素，並**向外放寬 2 個掃描像素**（寧可少切）
```

- **為何要淺色閘門**：使用者要求連米色 `#fdf6e8`（亮度 ≈ 246）、淺灰 `#eee`（238）都要處理，所以不能只認純白。但「任意純色都裁」會讓深色純底照（例如範例圖本身的暗紅背景）被裁進主體。亮度 ≥ 215 同時滿足兩者。
- **為何取四角而非固定白色**：柱狀留白時四角都落在左右白帶內、信箱式留白時四角都落在上下白帶內，兩種情形四角都同色，取樣穩定。
- **為何用「整列全為背景」而非逐點 bounding box**：bounding box 會被內容邊緣的 JPEG 振鈴雜訊撐大或被單一雜點誤導；整列規則遇到任何內容像素就停止，方向保守。實測範例圖內容邊界外一像素為 (255,255,251)，容差 12 涵蓋得住。
- **為何在縮圖上掃描**：4000×3000 的 `getImageData` 約 48MB；批次 30 張會明顯拖累。512px 掃描約 1MB，且縮放繪製時的平滑會讓邊界模糊——所以第 8 步向外放寬。

替代方案：Otsu/邊緣偵測自動找內容框（過度工程、對純色底照更危險）；固定只認 `≥244` 純白（無法滿足米色需求）。

### D2. 只裁單軸；四邊皆留白時不裁

```
marginL/R/T/B 佔該軸的比例
左右皆 ≥3% 且 上下皆 <3%  → 只裁左右
上下皆 ≥3% 且 左右皆 <3%  → 只裁上下
四邊皆 ≥3%                → 不裁（純色底商品照）
其他組合（含單邊）        → 不裁
```

純白／米色棚拍商品照四邊都有留白，若照裁會貼著商品切，接著 cover 放大 → 商品爆大且被外框斜幅蓋住。單軸規則正好把「被 letterbox/pillarbox 過的圖」與「純色底商品照」分開，也吻合需求描述的「左右空白邊，**或**上下空白邊」。

替代方案：設「最多裁 45%」上限——擋不住留白 20% 的白底商品照，鑑別力不足。

### D3. 去邊後仍走 cover 置中，且與去邊矩形合併為單次 `drawImage`

去邊矩形與 cover 裁切矩形都是來源影像上的矩形，交集後可用單一 `drawImage(bmp, sx, sy, sw, sh, 0, 0, 1000, 1000)` 完成，不需要中間畫布、不多一次重取樣。

範例圖：去邊後 771×1000 → `scale = max(1000/771, 1000/1000) = 1.297` → 來源取 771×771 → `drawImage(bmp, 114, 114.5, 771, 771, 0, 0, 1000, 1000)`。

**錨點固定置中**（使用者決定，主體為模型）。填滿正方形又不變形只有三種結局：裁掉、留白、變形；需求明確排除後兩者，因此上下各損失 148 輸出像素是必然結果，非缺陷。

### D4. 預覽以 selectedIndex + 遞增 token 防競態，並快取結果

```
state: selectedIndex, previewToken

select(i):
  selectedIndex = i
  const token = ++previewToken
  if (cache[i]) { 直接套用; return }
  const { blob, trim } = await compose(items[i].file)
  if (token !== previewToken) return          // 已被更晚的點擊取代，丟棄
  cache[i] = URL.createObjectURL(blob); 套用
```

- 大圖合成需 100~500ms，連點多張時回應順序不保證；沒有 token 會出現「點 C 顯示 B」。
- 快取單位為 1000×1000 JPEG（約 150KB），30 張約 4.5MB，可接受；`render()` 重新選檔時連同 `thumbUrl` 一併 `revokeObjectURL`。
- 快取的 blob 在按下產出時可直接重用，省一次合成（可選最佳化）。

### D5. 去邊結果顯示在清單，取代開關

`.dim` 那行由 `123 KB` 變為 `123 KB · 已去左右白邊`（未去邊時不顯示後半）。理由：使用者要掃過一批圖確認有沒有誤判，用看的比逐張點預覽快；同時避免多一個開關增加介面負擔。只說「有沒有去、去哪一軸」，不列實際像素數——像素數對判斷誤判沒有幫助，反而讓那行變吵。

## Risks / Trade-offs

- **淺色底、且主體不觸邊的商品照被誤判為留白** → 單軸規則使四邊留白的情形完全不裁；只有「恰好左右留白 ≥3% 而上下 <3%」才會觸發，且清單會顯示去邊量。
- **內容本身在邊緣有一條淺色帶（例如商品下方的白色反光台面延伸到底邊）** → 整列規則會把那一整列判為背景而多裁；但該列本來就無資訊，影響輕微。
- **範例圖這類頂天構圖，置中裁切會切掉頂端（兔耳）** → 已是使用者明示的取捨；預覽可逐張檢查，不滿意者自行前製。
- **縮圖掃描造成 ±2 掃描像素誤差**（4000px 原圖約 ±16 原始像素）→ 一律向外放寬，只會少裁不會多裁。
- **HEIC 等無法解碼的檔** → 去邊在 `createImageBitmap` 之後，既有錯誤路徑不變。

## Migration Plan

單檔工具、無持久化狀態，直接改 `index.html` 即可，無資料遷移。回滾＝還原該檔。既有輸出檔名規則、ZIP 打包、失敗處理均不變。

## Open Questions

- 去邊資訊是否也要寫進成品檔名或 ZIP 內的清單？目前傾向不要，維持檔名規則不變。
