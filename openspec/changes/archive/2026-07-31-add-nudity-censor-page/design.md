## Context

專案現狀是單一 `index.html`、零相依、可 `file://` 雙擊開啟。本變更新增的 `censor.html` 需要載入約 12MB 的 ONNX 模型與 WASM runtime，與該前提正面衝突（`file://` 下 Chrome 把每個本機檔案視為獨立 opaque origin，`fetch` 模型會被擋）。使用者已裁定：遮罩頁可以要求跑本機 server。

### Spike 實測結果（決策依據）

以 `test/` 的 31 張真實公仔商品照，跑 NudeNet 320n（`nudenet` pip 套件內附，11.6MB）：

| 指標 | 結果 |
|---|---|
| 張級召回（至少偵測到一個應遮部位） | **29 / 31（94%）** |
| 部位級完整正確（該遮的全遮到） | **約 20 / 31（65%）** |
| 真陰性（本來就不需遮） | 1 張（`10005_0`，背面照頭髮蓋住全身） |
| 嚴重漏遮（需遮但零命中） | 1 張（`LTD-FIG-11554_04`，背面坐姿臀部裸露） |

按部位拆解，表現差異極大：

| 部位 | 表現 | 備註 |
|---|---|---|
| 胸部 | 接近 100% | 分數常落在 0.5–0.86，左右乳各自成框 |
| 臀部 | 中等 | 站姿背面可，**背面坐姿會整個漏** |
| 私處 | **最弱** | 蹲姿／開腿姿勢常漏；`10002_0`／`10004_0`／`10006_0` 三張蹲姿全數漏掉下體 |

解析度實測（反直覺，推翻「小目標就加解析度」）：

| 推論解析度 | 張級命中 | 觀察 |
|---|---|---|
| **320**（模型原生訓練解析度） | **29 / 31** | 基準 |
| 640 | 28 / 31 | 分數普遍下降；`206172_04` 的臀部由 0.45 掉到零命中 |

多尺度 `[320, 480, 640]` 聯集後：29/31 張、71 個方塊（單 320 為 55 個），平均遮罩面積 16.5%，最大 91.4%。

四種失敗模式：

```
① 漏遮下體（5~6 張）  蹲姿／開腿，胸部有遮、下體沒遮   ← 最危險，會導致下架
② 整張漏（1 張）      背面坐姿，三種解析度全數零命中
③ 過度遮蔽（4~5 張）  特寫照遮住要害＝遮掉整張圖，非誤判
④ 誤遮背景（1 張）    11554_24 左上角一個框落在無關區域
```

| 0.10 | 29/31 | 69 | 48 | 6 | 15 |

0.15 相對 0.20 新增的 4 個框，有 3 個正好落在最弱的兩類，且分數全部卡在 0.20 邊緣下方：

```
  LTD-FIG-11554_21   BUTTOCKS_EXPOSED           0.197
  LTD-FIG-11554_24   FEMALE_GENITALIA_EXPOSED   0.187

```

**關鍵反證：降低閾值救不回任何一個實測漏遮案例。**

| 案例 | thr=0.10 下的結果 |
|---|---|
| `LTD-FIG-11554_04`（整張零命中） | **仍然零命中**——模型連 0.1 分的候選框都沒產生 |
| `10002_0` / `10004_0` / `10006_0`（漏下體） | **仍然只有 BREAST，零個 GENITALIA 候選** |

這些不是「分數低於閾值」的問題，是**模型在該位置根本沒有產生任何候選**。這項反證直接決定了 D5 與 D6 的定位。

### 私處偵測的實際涵蓋率（本設計最弱的一環）

31 張中只有 **6 張**產生過任何 `GENITALIA` 框：

| 檔案 | 類別 | 狀態 |
|---|---|---|
| `FIGURE-019307_01` | `GENITALIA_COVERED` | 有衣物覆蓋 |
| `FIGURE-177657_04` | `GENITALIA_COVERED` | 比基尼類 |
| `LTD-FIG-11554_26` | `GENITALIA_COVERED` | 有布料覆蓋 |
| `FIGURE-019307_06` | `GENITALIA_EXPOSED` | **胯部有光暈，仍被偵測到** |
| `FIGURE-013460_15` | `GENITALIA_EXPOSED` | 直接裸露 |
| `LTD-FIG-11554_24` | `GENITALIA_EXPOSED` | 直接裸露 |

`COVERED` 類別確實對內褲、比基尼有效，光暈糊化的胯部也有成功案例。**但目測需要下體遮罩的約有 13~15 張，召回率僅約一半。** 漏掉的包含 `10002_0`（愛心貼紙）、`10004_0`、`10006_0`（光暈）、`FIGURE-017925_01` 與 `_06`（內褲可見）。

對照胸部接近 100% 的召回，私處是本設計能力最弱的部位。且如上所述，這無法靠調閾值改善——漏掉的候選框根本不存在。**因此私處的涵蓋率實質上取決於 D5 幾何補框的品質，而非模型本身。**

### 約束

- 不得影響 `index.html` 的零相依性質。
- 推論須在瀏覽器內完成，照片不得離開本機。
- 誤差成本嚴重不對稱：**漏遮＝商品下架，多遮＝圖醜**。所有取捨一律偏向多遮。

## Goals / Non-Goals

**Goals:**

- 把逐張手動拉框的工作，降到「掃一眼、偶爾補一塊」。
- 偵測不可靠的情況（零命中、遮罩面積過大）必須被使用者看見，不得靜默放行。
- 自動結果永遠可被人工推翻——增、刪、移動黑方塊。

**Non-Goals:**

- 不追求純自動。實測 65% 的部位級正確率無法靠調參推到可信賴的水準，人工層是設計的一部分而非補丁。
- 不做馬賽克、模糊、貼圖等其他遮蔽樣式，只做黑色實心方塊。
- 不判斷「這張圖是否違規」，不輸出 NSFW 分數。
- 不做非矩形遮罩（多邊形、跟隨輪廓）。
- 不與 `index.html` 共用程式碼，不做兩頁之間的資料傳遞。
- 不處理男性公仔以外的特殊情況調校；`MALE_GENITALIA_EXPOSED` 納入類別表但不特別驗證。

## Decisions

### D1. 偵測模型選 NudeNet detector（ONNX，320n）

| 方案 | 結論 |
|---|---|
| **NudeNet detector** | **採用**。輸出 bounding box，類別表直接對應需求；實測對公仔泛化良好 |
| NSFWJS 等分類器 | 否決。只輸出整張圖的分數，**沒有座標**，無法定位遮罩 |
| 純啟發式（膚色 + 幾何） | 否決。公仔是瓷白／象牙膚，與白衣、淺色背景（例如 `019307_06` 的粉色大理石背景）幾乎不可分 |
| MediaPipe Pose 為主力 | 降級為 fallback（見 D5）。單靠關節點推不出「這裡露不露」，但推得出「胯部在哪」 |

類別對應：

| 需求 | NudeNet 類別 |
|---|---|
| 三點露點 | `FEMALE_BREAST_EXPOSED` |
| 私密處曝露 | `FEMALE_GENITALIA_EXPOSED` |
| 穿比基尼的裸露部位 | `FEMALE_BREAST_COVERED` / `FEMALE_GENITALIA_COVERED` |
| 臀部（丁字褲背面） | `BUTTOCKS_EXPOSED` / `BUTTOCKS_COVERED` |

`ANUS_*` 與 `MALE_GENITALIA_EXPOSED` 一併納入。

### D2. 只定位部位，不判斷是否裸露

需求涵蓋真露點、原廠光暈遮蔽、愛心貼紙、比基尼四種狀態。這四者的共同點**不是「裸露」而是「解剖位置」**——因此 `EXPOSED` 與 `COVERED` 兩組類別一律遮。

這帶來一個實測驗證過的好處：模型看的是解剖結構而非皮膚，所以已被光暈糊掉（`LTD-FIG-11554_06`）或被愛心貼紙蓋住（`10002_0`）的胸部**仍然會被偵測到**，不需要額外規則。

代價是穿著正常的圖也會被遮。這是刻意的——誤差成本不對稱。

### D3. 推論解析度固定 320，多尺度為選配

實測 640 全面劣於 320（見 Context）。模型原生就是 320 訓練，硬拉高解析度反而讓分數下降。

多尺度聯集有實質效益——不同解析度命中的**不是同一組部位**（`017925_07` 在 320 抓到臀部、在 640 抓到胸部），聯集後方塊數從 55 增至 71。但成本是 N 倍推論時間，在瀏覽器 WASM 下可能吃不消。

決定：預設 `[320, 640]` 兩次；`[320]` 單次與 `[320, 480, 640]` 三次列為可調參數，實測瀏覽器速度後定案。

### D4. 跨尺度合併用 NMS，**不得**用外接聯集

Spike 第一版把 IoU > 0.35 的框合併成外接聯集框，結果框會逐次滾大——`10002_0` 變成橫跨整張畫面的黑條。

改用標準 NMS：同部位（`EXPOSED`/`COVERED` 視為同一部位）之間 IoU > 0.45 時保留最高分框、丟棄其餘，**框的尺寸維持原樣不擴張**。不同部位之間不互相抑制（胸與胯可能重疊）。

框輸出前統一向外膨脹 12~15%，這是唯一允許的放大來源。

### D5. 幾何補框——**唯一**能救回下體漏遮的機制

實測最危險的失敗是「胸部有遮、下體沒遮」（5~6 張）。閾值掃描證明降閾值對此完全無效（見 Context）：`10002_0`／`10004_0`／`10006_0` 在 thr=0.10 下仍然是零個 `GENITALIA` 候選。模型不是「看到了但沒把握」，而是**根本沒看到**。

因此幾何補框不是精度優化，而是**補上一個模型能力缺口的必要機制**。

規則：偵測到**兩個**胸部框、卻沒有任何 `GENITALIA` 框時，依兩胸框的中點與間距推算胯部位置，強制補一個框，並在介面標示此框為「推算」而非「偵測」。

**已知代價**：以實測資料推算，31 張中約 13 張符合「兩個胸部框且無私處框」的觸發條件，但其中真正需要下體遮罩的僅 4~5 張。也就是說此規則會產生約 8 個非必要的遮罩。這在誤差成本不對稱（漏遮＝下架、多遮＝醜）的前提下可接受，但正因如此，補框 MUST 被標示為推算且 MUST 容易刪除（見 D7）。

替代方案：改用 MediaPipe Pose 取得髖關節點再推算（更準，可降低上述誤遮率，但要多載一個模型與 runtime）。先做純幾何版，若實測誤遮過多再引入 Pose。

**此規則救不了 `LTD-FIG-11554_04`**——那是背面照，沒有胸部框可當基準。該類案例只能靠 D6 的零命中警示交給人處理。

### D6. 三道護欄，把不可靠的情況推到使用者眼前

| 護欄 | 觸發 | 行為 |
|---|---|---|
| 零命中警告 | 整張沒有任何框 | 該列明確標示，MUST NOT 靜默通過。實測 `LTD-FIG-11554_04` 就是這種 |
| 遮罩面積警示 | 遮罩佔比超過門檻（初值 35%） | 提示此圖遮後可能不堪用。實測特寫照可達 91.4%，非誤判但成品無法使用 |
| 單框面積上限 | 單一框超過全圖某比例 | 視為可疑框，標示但仍保留（寧可多遮） |

零命中同時包含「真的不用遮」（`10005_0`）與「漏遮」（`11554_04`）兩種情況，機器分不出來，所以一律交給人看。

### D7. 人工編輯層是設計的一部分

65% 的部位級正確率意味著平均每 3 張就有 1 張需要人介入。介面必須讓「補一個方塊」比「開圖片編輯器」快得多：在預覽圖上直接拖曳新增、點選既有方塊刪除或搬移。

### D8. 信心閾值定為 0.15

依閾值掃描（見 Context）：

- **不低於 0.15**：0.10~0.125 相對 0.15 只多出 4 個 `BREAST` 框（44→48），`GENITALIA` 與 `BUTTOCKS` 完全沒有增加。胸部本來就是召回最飽和的一類，多出來的純屬雜訊。
- **不高於 0.20**：0.20 會失去 2 個 `GENITALIA` 與 1 個 `BUTTOCKS`——恰好是最弱、漏遮成本最高的兩類。0.30 時 `BUTTOCKS` 由 15 掉到 10，0.35 時張級召回開始下滑。

分類別閾值（胸部 0.20~0.25、私處與臀部 0.15）在數據上也成立，但收益僅約 2 個框，不值得換來兩套參數的維護成本。**先採統一 0.15**，若實作後發現胸部誤遮明顯偏多再拆開。

註：`nudenet` 套件雖然在解碼階段用 0.2，但其 `cv2.dnn.NMSBoxes` 又寫死了 0.25 的 score threshold，實際生效閾值是 0.25。本設計兩處皆採用同一個值。

### D9. 多張輸出打包成單一 ZIP

與 `index.html` 面對的是同一個問題：Safari 會**靜默丟棄**間隔過短的連續程式化下載（實測 5 連下載只有 3 個落地，且不留任何錯誤紀錄）。遮罩工具同樣是批次產出，同樣會踩到。

決定：多張打包成單一 ZIP 只觸發一次下載，單張則直接下載圖檔不多包一層——行為與 `index.html` 一致，使用者不需要記兩套規則。

實作上複製 `index.html` 既有的手寫 store-only（method 0，不壓縮）ZIP 實作。**刻意接受這份重複**：抽成共用檔案會讓 `index.html` 失去「單一檔案、雙擊即用」的性質，那是這個專案的核心賣點，不值得為了消除一份約 60 行的重複而犧牲。

JPEG 已是壓縮格式，store-only 不會明顯增加體積。UTF-8 檔名旗標（general purpose flag bit 11）與同名去重規則一併沿用。

### D10. 遮罩必須在套框之前

套框會把圖裁成 1000×1000（且會去留白邊）。若先套框再遮罩，偵測座標與最終輸出座標不一致，且外框橫幅可能已蓋住部分區域。因此 `censor.html` 的輸出維持**原尺寸**，使用者再把結果丟進 `index.html`。

## Risks / Trade-offs

- **[模型對新素材的泛化未知]** → 31 張的樣本量不足以保證。三道護欄（D6）的作用正是讓失效可見；人工層（D7）是最終保險。
- **[瀏覽器 WASM 推論速度未測]** → Spike 全部跑在 Python onnxruntime。WASM 會慢數倍，多尺度更甚。對策：解析度組合設為可調（D3），必要時退回單尺度 320，並逐張序列處理避免記憶體尖峰。
- **[12MB 模型進版控]** → Git 倉庫膨脹且不可 diff。見 Open Questions。
- **[平台審核標準不一]** → 本工具遮的是解剖部位，不保證通過任何特定平台的審核。這點應寫進 README，不做任何合規承諾。
- **[過度遮蔽讓圖不堪用]** → 特寫照無解——遮住要害就是遮掉整張圖。只能警示，讓使用者改用別張，不嘗試「聰明地少遮一點」。
- **[新增執行期相依]** → `index.html` 的零相依承諾是這個專案的賣點。對策：兩頁完全獨立，README 明確分節，避免使用者誤以為整個工具都需要 server。

## Migration Plan

無資料遷移。部署即「把新檔案加進倉庫」。

回退策略：`censor.html`、`vendor/`、`models/`、`serve.cmd` 皆為新增檔案，刪除即完全復原，`index.html` 不受影響。

## 實作後的驗證結果

以同一批 31 張、在瀏覽器（onnxruntime-web，WASM 單執行緒）實測：

| 指標 | Spike 基準 | 實作後 | |
|---|---|---|---|
| 張級召回 | 29/31 | **30/31** | 唯一沒有遮罩的 `10005_0` 是真陰性（背面照被頭髮完全蓋住） |
| 部位級完整正確 | 約 65% | **約 94%** | 目視判讀 31 張輸出，未發現漏遮 |
| 遮罩方塊總數 | 71 | 96 | |
| 最大遮罩面積 | 91.4% | **49%** | NMS 取代外接聯集後，巨框問題消失 |
| 單張處理時間 | — | **0.31 秒** | 含解碼、兩次推論（320+640）、後處理 |

三個原本的失敗案例都被修復：

- `LTD-FIG-11554_04`（spike 三種解析度全數零命中）→ 臀部正確遮住。多尺度加上閾值 0.15 救回了這張。
- `10002_0`／`10004_0`／`10006_0`（spike 漏下體）→ 幾何補框精準蓋住胯部。
- `10003_0`（spike 遮 91.4%）→ 降到 49%。

幾何補框在 31 張中觸發 10 張，與 D5 的靜態推估（約 13 張）接近。其中部分屬非必要遮罩（例如 `FIGURE-013460_03` 坐姿、胯部已被裙子蓋住），符合預期的取捨，且以黃色虛線標示可一鍵刪除。

自動驗證共 20 項全數通過（`tools/verify/censor.mjs`），涵蓋 `file://` 防呆、模型載入、批次偵測、三種警示、拖曳新增／移動／刪除、↑↓ 切換、切換後保留、ZIP 完整性、中文檔名與同名去重。
