## Context

`money-sorry` 原本是一個 60KB、零依賴、雙擊即用的批次套框工具。這個 change 要在它旁邊加上一個**批次遮罩**工具，處理成人向 figure 商品照上架前的裸露部位遮蔽。

**約束**（多數繼承自既有專案，一條是新的）：

- 單人自用、無帳號、無後端、**照片不離開這台電腦**
- 必須能離線、雙擊即用（`file://` 協定）
- 每天 100 張以上，人工逐張畫框不可行
- **漏遮是靜默失敗**：自己不會發現，等平台通知才知道。這與 `photo-framing` design.md 決策 4 處理的「Safari 靜默丟棄下載」是同一類失敗模式，套用同樣的標準——不接受靠信心分數的時序／機率型啟發式
- 成本嚴重不對稱：多遮 = 圖醜、一秒看出、重畫即可；漏遮 = 下架／封帳號

**實測素材**：`test/` 下 31 張真實商品照，涵蓋 8 個商品。尺寸從 302×800 到 1000×1300，長寬比 0.38～1.54。姿勢涵蓋站、坐、跪、趴、蹲、M字腿；視角涵蓋正面、背面、側面、半身特寫、局部大特寫；背景涵蓋粉／灰／褐大理石、暗紅、哥德暗景、白毛毯。

**三個 spike 的結論**（全部在上述 31 張上實測，數字見下方各決策）：

```
S1  file:// 下零 fetch 載入 MoveNet          PASS
S2  三個模型變體的關鍵點信心比較              Thunder 勝
S3  遮罩落點的逐張人工判讀                    危險漏遮 0/31
```

實作完成後另以使用者提供的**人工遮罩成品**做像素級比對（見決策 13），並把所有驗證固化成 Playwright 測試。

## Goals / Non-Goals

**Goals:**

- 100 張照片在數分鐘內完成遮罩，且**保證不會靜默輸出未遮的圖**
- 保住 `index.html` 的 60KB／零依賴／雙擊即用不受污染
- 遮罩工具本身也要能離線、雙擊即用、照片不離開本機
- 偵測失敗時**明確舉手**，而不是產生看似合理但錯誤的遮罩

**Non-Goals:**

- 全自動無人複核。人工複核是這個設計的一部分，不是過渡期的權宜
- 遮罩樣式的多樣性（馬賽克／模糊／貼圖）——只有純黑軸對齊矩形
- 自動判斷「這張有沒有裸露」（見決策 6）
- 遮罩範本存檔與跨圖重用（實測 `019307_01` 穿內褲、`019307_06` 沒穿，同商品同站姿需求完全不同）
- 在 `censor.html` 內做 cover 裁切與套框（見決策 10）
- 支援非 WebGL 環境

## Decisions

### 1. 用姿態關鍵點定位，而不是 NSFW 物件偵測器

**選擇**：MoveNet 姿態估計 → 從肩／髖／膝的空間關係推導遮罩矩形。

**理由**：

`test/` 裡有相當比例的圖，**乳頭與胯部已經被廠商用白色光暈或愛心貼紙蓋過一次**（`10003_0`、`10004_0`、`10006_0`、`11554_26` 等）。NudeNet 這類偵測器的類別是成對的（`FEMALE_BREAST_EXPOSED` ↔ `FEMALE_BREAST_COVERED`），輸入正好落在它最沒把握的地帶。姿態模型看的是肩膀和髖部，對光暈完全無感。

第二個理由是**「M字腿」不是身體部位而是姿勢**。NudeNet 的 18 個類別裡沒有姿勢類、也沒有大腿類，靠類別聯集拼不出目標那條橫跨 61.6% 畫面寬的大遮罩。用關鍵點反而有乾淨的判準（決策 8）。

**替代方案**：

- NudeNet ONNX：在已被光暈遮蓋的圖上最弱，且缺姿勢類別；另需 ORT-web，破壞決策 2
- 背景減除 + 膚色啟發式（零依賴）：實測 `10006_0` 背景 RGB(164,143,148) 與蒼白膚色 RGB(240,225,215) 太近，可用容差視窗只有 70～90 一小段，`tol=30` 時整張爆掉。換個背景就要重調，屬於會靜默出錯的參數
- 雲端 VLM：違反「照片不離開這台電腦」，且成人商品圖送 API 大機率被內容政策擋掉

**保留的門**：NudeNet 的強項（局部特寫、無人體脈絡）正好補在姿態模型的弱項上。若日後決策 5 擋下的比例太高，可考慮把它加成 OR-gate 的第二意見（只增加 recall，不減少）。目前不做。

### 2. TensorFlow.js + WebGL backend，權重以 base64 內嵌

**選擇**：`tf.loadGraphModel(tf.io.fromMemory({...}))`，WebGL backend，權重 base64 內嵌於 HTML。

**理由**：這是被 `file://` 逼出來的，不是偏好。

```
TF.js + WebGL backend            ORT-web / MediaPipe
─────────────────────            ───────────────────
純 JS + GLSL shader              必須載入 .wasm 二進位
    ↓                                ↓
沒有任何外部二進位檔要載          預設用 fetch() 抓
    ↓                                ↓
權重 base64 → ArrayBuffer         file:// 下 opaque origin 擋死
→ tf.io.fromMemory 直接餵          且 Worker 被擋、
    ↓                             SharedArrayBuffer 需 COOP/COEP
零 fetch、雙擊即用 ✅              （file:// 拿不到）❌
```

**S1 實測（headless Chrome，`file://`）**：

| 項目 | 結果 |
|---|---|
| protocol | `file:` |
| WebGL renderer | ANGLE (Apple, ANGLE Metal Renderer: Apple M4) — 真 GPU |
| backend | `webgl`, tfjs 4.22.0 |
| 權重 | 11.90 MB 自 base64 解出 |
| 模型載入 | 0.06 s |
| **fetch / XHR / WebSocket 呼叫次數** | **0**（三者皆被攔截器包成 throw，一次都沒觸發）|
| 開啟網頁 → 模型可用 | 2.7 s |
| 單張推論（20 次中位數）| 16–22 ms |

100 張純推論約 2 秒。效能完全不是瓶頸。

**替代方案**：起本機 HTTP server（破壞雙擊即用）、改寫成 Node CLI（破壞既有專案形態，且工作區頂層有 TCC 限制）。

**代價**：`censor.html` 約 18MB、開啟等 2.7 秒。透過決策 10 把這個代價隔離在獨立檔案裡。

### 3. MoveNet SinglePose **Thunder**，不是 Lightning 也不是 MultiPose

**選擇**：SinglePose Thunder v4（256×256 輸入，權重 12MB）。

**S2 實測（31 張，以肩／髖信心分級）**：

| 模型 | 權重 | 🟢 | 🟡 | 🔴 |
|---|---|---|---|---|
| SinglePose Lightning (192²) | 4.7 MB | 81% | 16% | 3% |
| **SinglePose Thunder (256²)** | **12 MB** | **84%** | **16%** | **0%** |
| MultiPose Lightning | 9.3 MB | 58% | 26% | 16% |

**MultiPose 明顯最差，這推翻了探索初期的假設。** 當時擔心 SinglePose 的方形輸入會讓 302×800、800×520 這類極端長寬比失真，而 MultiPose 吃非方形輸入。實測結果相反——Thunder 的置中 pad + 較高輸入解析度贏過 MultiPose 的多人偵測管線。

Lightning 只小 7MB 但多一張紅、綠少 3%。以「多遮不痛、漏遮致命」的成本結構，換 7MB 檔案大小不划算。

**前處理**：置中 pad 成正方形 → resize 到 256×256 → `int32`（MoveNet 輸入 dtype 是 `DT_INT32`，不做正規化）。關鍵點輸出為 padded square 的正規化座標，需扣掉 pad 位移再除以原圖尺寸換回原圖座標。

### 4. 結構合理性檢查——信心分數會騙人

**選擇**：在信心閘門之外，額外做多項幾何合理性檢查；任一不過即擋下轉人工，**不產生遮罩**。

**理由**：這是整個 spike 最重要的發現。**高信心 ≠ 位置正確。**

`013460_21` 是一張沒有任何人體脈絡的胯部大特寫（沒有臉、沒有肩膀、沒有可辨識人形）。Thunder 在上面**幻覺出 0.33 信心的肩膀對**，只用信心閘門會判為可用，然後在毫無意義的位置畫一個遮罩——而使用者在複核牆上看到「系統有給建議」，正是最容易掃過去的情況。

各項檢查與實測擋下情形：

| 檢查 | 條件 | 擋下 |
|---|---|---|
| 關鍵點塌陷 | 有效點包圍盒面積 / 圖片面積 < 4% | — |
| 軀幹比例異常 | `torso / 肩寬` 不在 [0.55, 3.2] | `013460_01`、`11554_10`、`177657_02`、`019307_04` |
| 半身模式無臉 | 無髖部關鍵點 且 臉部信心 < 0.30 | `013460_21` (face 0.19) |
| 半身模式肩部信心不足 | 無髖部 且 `min(左肩,右肩) < 0.40` | `11554_06`（0.40 邊界）|
| 肩部信心不足 | `min(左肩,右肩) < 0.25` | `10005_0` |
| **軀幹接近水平** | 身體軸偏離垂直 > 45°（見決策 7c）| `206175_01` (73°)、`206175_13` (77°) |

**「無髖部 + 無臉」是局部特寫的可靠指紋。** 對照組 `10003_0` 同為半身特寫但臉清楚（0.49），順利通過並正確遮到胸部。這條規則精準區分了「半身照」與「局部特寫」，剛好對應使用者估計的「局部特寫約佔上架量一成」。

**代價**：31 張裡擋下 9 張（29%）。這是刻意付出的成本，換到「危險漏遮 0/31」。

### 5. 側面姿勢一律擋下，不做搶救

**選擇**：`torso / 肩寬 > 3.2` 一律擋下，不改用更穩健的比例尺去搶救。

**理由**：被擋下的 6 張裡有 4 張是同一個原因——側面視角把肩寬的投影壓扁了，而**肩寬正是所有幾何推導的比例尺**。尺標一崩，遮罩就會塌成一小團。上一輪 `177657_02`（蹲踞背面）就是這樣失敗的：關鍵點塌成一團、臀部帶完全沒碰到臀部，而信心分數看起來還好。

技術上可以改用 `max(肩寬, 髖寬, 軀幹長×0.55)` 當比例尺去搶救這 4 張。**但那是用一個更不穩的估計去換自動率。** 在漏遮成本是封帳號的前提下，讓它明確舉手是更好的交易。

**這是設計決定，不是還沒修的缺陷。** 若日後量體變大到 19% 人工不可接受，再回頭做這個搶救，並且必須重跑 S3 確認搶救沒有把「明確失敗」變成「隱性錯誤」。

### 6. 不做「是否裸露」的自動判斷，一律出遮罩建議

**選擇**：每張通過結構檢查的圖都產生遮罩建議，穿衣服的由人工刪框。

**理由**：原本設計了「臉部自校正膚色閘門」——用鼻部取樣得到這尊 figure 自己的膚色作為色卡，再統計遮罩帶內符合該色度的像素比例。它繞開了全域膚色模型的所有調參問題，在多數圖上也確實合理（`013460_15` 全裸 75%、`206172_01` 90%、`019307_01` 濕襯衫 53%）。

**但實測有假陰性**：

```
017925_01   0% / 0%   ← 胸部明顯外露
177657_04   0% / 0%   ← 同上
017925_07   1% / 0%
```

推測是鼻部關鍵點落在帽子或瀏海上，參考色整個偏掉。**假陰性正是最危險的方向**——它會讓一張該遮的圖判定為不用遮。

而使用者的需求本身給了更好的解：既然「有裸露每張都要遮」、賣的又幾乎清一色是這類商品，那就**不要這個閘門**。刪一個框是一次點擊，假陰性是帳號。

**替代方案**：修膚色演算法（改用臉頰而非鼻部、多點取樣、加入亮度不變量）——可行，但為了省下少數幾次點擊而引入一個會假陰性的判斷，方向錯誤。

### 7. 軸向感知幾何：用身體自己的軸，不用畫面的上下

**選擇**：以「肩中點 → 髖中點」向量作為身體軸，遮罩帶沿軸定位、垂直軸展開，最後把旋轉矩形取外接軸對齊矩形。

**理由**：斜倚與坐姿的軀幹並非垂直（實測偏離垂直可達 26°）。若假設軀幹垂直，遮罩會偏離目標。軸向感知讓遮罩帶跟著軀幹轉。

> 偏離垂直**超過 45°** 的趴跪／躺臥姿勢不在此列——那類姿勢的臀部幾何與直立姿勢根本不同，由決策 7c 擋下轉人工，不進入幾何推導。

```
   垂直軀幹                        傾斜軀幹（軸向感知跟著轉）
   ┌─────────────┐                ┌──────────────────────┐
   │   ●─────●   │ 肩             │        ●              │
   │   ┃▓▓▓▓▓┃   │ ← 胸部帶        │   ●   ╱ ╲             │
   │   ┃     ┃   │                │  ╱ ╲ ╱   ●  ← 髖      │
   │   ●─────●   │ 髖             │ 肩  ▓▓▓▓▓▓            │
   └─────────────┘                └──────────────────────┘
```

「最後取外接軸對齊矩形」這步把旋轉的複雜度吃掉了——外接矩形必定 ≥ 旋轉矩形，而**多遮是安全方向**，且輸出需求本來就是軸對齊黑矩形。

**尺度**：所有帶的位置與寬度都以**肩寬**為單位表示，因此自動隨圖中人物大小縮放。實測 `10003_0`（半身特寫）的胸部帶明顯比全身圖大，正是因為肩寬在畫面中佔比大——比例尺自己會對。

**正／背二分**：`左肩.x > 右肩.x` 為正面（MoveNet 的左右是人物自身的左右）。正面 → 胯部帶；背面 → 臀部帶（往下偏移、寬度 ×1.25）。`206172_04`（純背面站姿）的臀部帶落點精準。

> **曾經有第三類「側面」，後來移除了。** 判準是 `肩寬/軀幹長 < 0.62` 或左右耳信心差 > 0.42。當時只憑肉眼印象定值，並自我安慰「側面 = 更寬的帶，屬於安全方向的失效」。用使用者提供的人工遮罩成品比對時才發現代價：誤判成側面會多吃一個 ×1.55，把下半身帶推到滿版（面積是參考的 3.1 倍）。
>
> 回頭量了 23 張的 `肩寬/軀幹長`：**從 0.386 連續分佈到 0.930，沒有任何分界**，而且已知正面的 `019307_06`（0.447）比已知側面的 `206175_13`（0.774）還低；純側面的 `206175_01` 兩耳信心差是 0.00。**這個特徵根本沒有鑑別力**，門檻 0.62 恰好落在正面姿勢的正常範圍中央。移除之，並把正面帶本身放寬 ×1.15 當補償。

### 7b. 下半身帶錨定在髖部，不是肩線的固定倍數

**選擇**：令 `hipT = 軀幹長 / 肩寬`，下半身帶為 `t ∈ [hipT − 0.35, hipT + 1.00]`；起點另受 `t0 ≤ 胸部帶終點` 約束。

**理由**：原本寫死 `t ∈ [1.35, 2.30]`，隱含假設「髖部大約在 1.7 倍肩寬處」。但結構檢查允許 `軀幹長/肩寬 ∈ [0.55, 3.2]`——實測 `019307_06` 是 2.23，髖部遠低於固定倍數所預期，**下半身帶整條停在胯部上方，只蓋到 35%**。這是被 Playwright 的裸露區域覆蓋測試抓出來的真實漏遮。

改成錨定髖部後同一張升到 78%，再把 `dt1` 從 0.80 放到 1.00 才完全覆蓋。

**「起點不晚於胸部帶終點」是第二個修正**：錨定髖部後，長軀幹體型的下半身帶起點可能落在胸部帶終點之後，兩帶之間留下一條沒遮到的橫縫（實測 `206172_04` 有 0.015 畫面高的裸露縫）。夾住起點即可保證兩帶相接。

### 7c. 軀幹接近水平的姿勢一律擋下

**選擇**：身體軸偏離垂直 > 45° 即判定結構不合理，轉人工。

**理由**：趴跪抬臀的姿勢裡，臀部相對髖部的位置與直立姿勢完全不同——臀部同時往軸向與垂直軸方向鼓出。實測 `206175_01` 即使把軸向延伸到 2.80 也只蓋到 78%，而再放大就會嚴重影響所有其他圖。

這個特徵**分得非常乾淨**：31 張裡趴跪姿是 73° 與 77°，其餘最高只有 26°，中間空了 47 度。與決策 5 同一個原則——分不出來就明確舉手，不要產生看似合理卻漏遮的遮罩。代價是 🔴 從 7 張增為 9 張（29%）。

### 8. M字腿：兩個不等式 + 硬性 clamp

**選擇**：

```
膝高於髖：  min(左膝.y, 右膝.y) < 髖中線.y + 0.25 × 髖寬
兩膝張開：  |左膝.x − 右膝.x| > 1.6 × 髖寬

兩條同時成立 → 下半身帶改用膝距定寬：
    半寬 = (膝距 / 2) × 0.75 / 肩寬
    沿軸範圍 t ∈ [hipT − 0.25, hipT + 1.20]
```

**上限必須在所有倍率之後才套用。** 第一版寫成 `min(膝距換算, 2.2)` 然後才乘朝向倍率，結果 `1.49 × 1.55 = 2.31` 直接突破上限，算出 1086px 寬再被畫面邊界截斷成滿版——**上限形同虛設**。現在統一在 `rect()` 裡以 1.95 夾住，並額外限制矩形寬度不得超過畫面的 92%（超過就以中心等量收窄，而不是讓它撐到兩端）。

實測 31 張中 9 張觸發，涵蓋兩尊兔女郎、馬桶警察、惡魔坐姿等，判定正確。

`0.75` 係數是必要的：直接用 `膝距/2` 當半寬，在 `10006_0` 上算出的矩形寬度超過整張圖寬（參考目標只要 61.6%）。所有矩形另外**外擴 12% 後 clamp 到圖片邊界**。

### 9. 複核牆與輸出鎖死

**選擇**：全自動跑完後進入分級複核介面；🔴 項目未逐張處理完，輸出鍵鎖死。

```
100 張 ──推論 3 秒──▶ ┌──── 複核牆 ────────────────────┐
                      │ 🟢 68%  掃視確認       ~100 秒  │
                      │ 🟡  3%  拖曳微調 ×5s    ~15 秒  │
                      │ 🔴 29%  手動畫框 ×10s  ~290 秒  │
                      └────────────┬───────────────────┘
                                   ▼
                      🔴 未清空 → 輸出鍵 disabled
```

**理由**：在 100 張／天的量級，逐張畫 200 個框不可行，但逐張**稽核**可行。使用者的工作從「畫框」變成「審框」。

輸出鎖死那條直接繼承 `photo-framing` design.md 決策 4 的精神：**不接受靜默失敗**。偵測不出來就明確擋住，不要輸出一張看起來正常但沒遮的圖。

**實測結果（31 張，經 Playwright 自動驗證 + 逐張肉眼判讀）**：

| 結果 | 張數 | 佔比 |
|---|---|---|
| 🟢 關鍵點信心充足，遮罩位置正確 | 21 | 68% |
| 🟡 半身模式或關鍵點部分殘缺 | 1 | 3% |
| 🔴 結構檢查主動擋下 → 人工 | 9 | 29% |
| ⛔ **有外露、未擋下、又沒蓋到** | **0** | **0%** |

最後一行是唯一真正重要的數字，且已固化為 `tools/verify/censor.spec.js` 的自動測試。

**人力估算（100 張）**：推論約 3 秒 + 複核約 7 分鐘（68% 掃視確認、3% 微調、29% 手動畫框）。

### 10. 兩個各自獨立的工具，不是一條管線

**選擇**：`censor.html` 與 `index.html` 是**兩個用途不同的獨立工具**。遮罩的輸出就是完成品（與來源同尺寸的已遮圖），不預設會再送去套框。

**理由**：使用者確認「做遮罩的不一定會要上邊框圖」——需要遮罩與需要套框是兩件互不蘊含的事。把它們設計成管線會強加一個不存在的順序。

`index.html` 是 60KB、零依賴、雙擊即用、三年後還能開。把 18MB 的模型塞進去會毀掉它的每一項性質，而大多數商品照根本不需要遮罩。反過來，`censor.html` 內建套框也是錯的：`photo-framing` spec 對 cover 裁切、去白邊、單次 `drawImage` 不重複取樣有相當細的規定，複製一份必然漂移，而且會強迫只想要遮罩的使用情境接受一個不想要的外框。

```
       ┌─▶ censor.html ─▶ masked/（已遮，原尺寸）
商品照 ─┤              └─▶ raw/（完全原檔，位元組不變）
       │
       └─▶ index.html  ─▶ 1000×1000 已套框成品

兩條路各自完整。需要兩者時使用者自行把 masked/ 的檔案餵給 index.html，
但那是使用者的選擇，不是工具預設的流程。
```

**推論**：因為遮罩輸出是完成品而非中間產物，`censor.html` **必須維持來源尺寸與長寬比**，不得為了「反正之後會裁成 1000×1000」而擅自裁切或縮放。

**替代方案**：把套框邏輯抽成共用 `.js` 讓兩邊 `<script src>` 進去。已否決——`index.html` 就得從單一檔案變成兩個檔案，那是它最核心的性質，而收益只在「兩者都要」的情境下才存在。

### 11. 遮罩座標存原圖空間，繪製時做仿射變換

**選擇**：遮罩矩形以**原圖像素座標**儲存；輸出時把矩形四角走與照片相同的仿射變換到目的座標。

**理由**：使用者指定「原圖座標畫框」。若日後要在同一個管線裡接上 cover 裁切，這個選擇可以避免與 `photo-framing` spec「去邊矩形與 cover 裁切矩形合併為單一 `drawImage`，不經中間畫布重複取樣」衝突——純黑實心矩形做座標變換是精確且無損的，不需要中間畫布。

繪製順序固定為：**白底 → 照片 → 黑色遮罩 → （若有）外框**。

### 12. raw 版是位元組層級的原檔複製

**選擇**：`raw/` 內的檔案是來源檔的**完整複製**，不重新編碼、不裁切、不套框、副檔名不變。

**理由**：使用者明確要求「完全原檔」。重新編碼會造成世代損失，也讓「留存原始素材」這個目的失效。實作上直接把 `File` 的 bytes 寫進 ZIP，不經過 canvas。

### 13. 以使用者的人工遮罩成品作為驗收基準

**選擇**：把使用者手工做好的兩張遮罩成品放進 `test/reference/`，用 Playwright 量出其中的純黑矩形，要求我們的遮罩**完全包住**它們。

**理由**：這是唯一的外部真值。工具自己算出來的東西沒辦法自證正確，逐張肉眼判讀又無法自動重跑。

參考成品是 1000×1000、來源是 1000×1300，但**正規化座標在軸對齊縮放下不變**，可以直接比較，不必還原壓縮比例。

驗收條件分兩層：

| 層次 | 條件 | 性質 |
|---|---|---|
| **覆蓋** | 參考區塊必須被 100% 覆蓋 | 安全性，不可妥協 |
| **面積** | 聯集面積 < 參考的 2.6 倍 | 品質，只用來擋住「幾何算爆」|

面積比目前實測 2.3～2.4 倍，主要來自胸部帶比參考高約一倍（我們從鎖骨蓋到乳下緣，使用者只蓋乳頭一帶）。這是刻意的取捨——放寬胸部帶是為了涵蓋各種胸型與角度，代價是圖比使用者手工的更醜。若要更貼近參考，調小 `G.chest.t1` 即可，但必須重跑覆蓋測試確認沒有掉出 100%。

**這條測試立刻回本**：它抓出了「側面誤判導致滿版」（面積 3.1 倍）與「上限套用順序錯誤」兩個缺陷，都是肉眼判讀時看過卻沒察覺的。

## Risks / Trade-offs

| 風險 | 緩解 |
|---|---|
| **信心分數會騙人**——高信心的關鍵點仍可能位置錯亂（實測 `013460_15` 膝蓋信心 0.86 卻目視錯位）| 結構合理性檢查（決策 4）+ 複核牆必須疊上遮罩讓人**看位置**而非看分數；分級只是排序輔助，不是通過憑證 |
| 19% 需人工，量體變大時線性增加 | 目前 100 張約 6 分鐘可接受。真的不夠時的第一手是決策 5 的側面搶救（需重跑 S3 驗證），第二手是決策 1 保留的 NudeNet OR-gate |
| MoveNet 是真人照訓練的，動漫 figure 屬於分布外 | 已在 31 張真實素材上實測，非推測。但**新商品線（例如非人形、獸耳全身毛、機械體）可能落在未驗證區域**；擴充素材後應重跑 S3 |
| `censor.html` 約 18MB，開啟 2.7 秒 | 隔離在獨立檔案（決策 10），`index.html` 不受影響 |
| 依賴 WebGL；無 WebGL 環境會退回 CPU backend 而極慢 | 啟動時偵測 backend，非 `webgl` 時明確警告並顯示預估耗時，不靜默降速 |
| 引入 TF.js 與模型權重，破壞了專案原本「零依賴」的性質 | 兩者皆內嵌、執行期零網路，沒有 CDN 過期或 npm 供應鏈風險。權重原始檔留在 `assets/model/` 供換模型時重新內嵌 |
| 換模型需重新產生 base64 | 與既有的換外框流程同構，步驟記入 README |
| 一張圖有兩尊 figure 時 SinglePose 只抓一個 | 現有素材未出現。若出現，第二尊會完全沒有遮罩且不被結構檢查擋下——**這是目前唯一已知的靜默漏遮路徑**，需在複核牆的說明中明示，並列為擴充素材後的優先驗證項 |
| 遮罩太醜影響賣相 | 純黑矩形是使用者指定的樣式，且對平台審核最安全（明確遮擋，不會被判定為試圖規避）|

## Migration Plan

新增功能，無既有資料或使用者需要遷移。

- **部署**：把 `censor.html` 放進專案目錄即可，雙擊開啟
- **回滾**：刪除 `censor.html` 與 `assets/model/`。`index.html` 與 `openspec/specs/photo-framing/` 全程未被觸碰，不需要任何回復動作
